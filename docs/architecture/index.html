How Enso is actually put together

Enso looks like one app, but it's really two programs shaking hands: a Swift app that draws all the chrome (sidebar, tabs, palettes), and libghostty — Ghostty's terminal engine — which does the actual terminal-ing. Once you see that split, every file in the repo has an obvious home.

When you press a key in Enso, here's the whole journey. The Swift layers are the ones you'll edit 95% of the time; the Zig layer is a prebuilt library you mostly just talk to.

Sidebar, tabs, spaces, command palette, settings. Ordinary SwiftUI views reading from one shared store.

EnsoApp.swift START HERE
macos/Enso/EnsoApp.swift
177 lines

The @main entry point — creates every long-lived object and injects them into SwiftUI.

The real deal

This is the app's dependency graph in one file: it constructs the session store, the Ghostty runtime, the update controller, etc., and passes them down as environment objects. If you ever wonder "who owns X?", the answer starts here.

It also picks the Application Support folder per build identity — Dev, Next, and stable Enso each get their own, because two running builds sharing one state.json would silently overwrite each other's tabs (last writer wins).

QuitGuard.swift

The "Quit Enso? You have running sessions" confirmation dialog.

The real deal

GhosttyRuntime.swift
macos/Enso/Ghostty/GhosttyRuntime.swift
306 lines

Boots libghostty once, loads its config, and pumps its event loop.

The real deal

Owns the single ghostty_app_t instance: global init, config loading (your regular Ghostty config file works here — that's why the terminal keeps your Ghostty theme), and a main-thread tick loop driven by ghostty wakeups.

The tricky part it handles: libghostty's C callbacks fire on its internal threads, so this file catches them in nonisolated code and hops to the main actor before touching any UI.

GhosttySurfaceView.swift
macos/Enso/Ghostty/GhosttySurfaceView.swift
608 lines

The actual terminal rectangle — an NSView that libghostty renders into.

The real deal

One instance = one live terminal ("surface"). libghostty owns the PTY, the shell process, and the Metal rendering; this view's job is to feed it input, focus, and size changes — keystrokes down, resize events down, "the title changed" notifications up.

It's 600 lines because keyboard handling on macOS is genuinely fiddly: dead keys, IME, modifier quirks, mouse reporting, drag-and-drop of file paths. If a keystroke behaves oddly, look here first.

GhosttySurfaceManager.swift
macos/Enso/Ghostty/GhosttySurfaceManager.swift
65 lines

Keeps one live surface per tab, so switching tabs re-attaches the same running shell.

The real deal

Tiny file, load-bearing idea: SwiftUI happily destroys and recreates views, but you can't "recreate" a running shell. So surfaces live outside the view hierarchy in this manager, keyed by session ID, and views merely borrow them. That's why switching tabs doesn't restart your process.

GhosttyTerminalHostView.swift

The real deal

The adapter between worlds: SwiftUI on the outside, AppKit's GhosttySurfaceView on the inside. Nearly all "why is the terminal not resizing/focusing" bugs trace to this seam or the surface view behind it.

TerminalSession.swift START HERE
macos/Enso/Models/TerminalSession.swift
299 lines

The core nouns: a session (tab), a space (sidebar page), folders, and the pinned zone.

The real deal

The data model in one sentence: a space is one swipeable sidebar page, holding a pinned zone plus ephemeral tabs. The pinned zone is a single ordered list where loose tabs and folders interleave freely; folders hold tabs and cannot nest. Ephemeral (unpinned) tabs expire after 24 hours.

These types are Codable — what you see here is literally the schema of state.json on disk.

TabProcess.swift
macos/Enso/Models/TabProcess.swift
148 lines

"What's running in this tab?" — the detection result that decides each tab's icon.

The real deal

Combines two signals — shell-integration title events and the pty's resolved foreground process — into one verdict. Agents (Claude, Codex, Gemini, Ollama) get brand artwork, known tools (vim, ssh, git, docker) get SF Symbol glyphs, an unrecognized live process gets the running-blue dot, and an idle shell gets the grey one.

TerminalSessionStore.swift START HERE
macos/Enso/Stores/TerminalSessionStore.swift
1,059 lines

The single source of truth: all spaces, tabs, folders, selection — plus persistence.

The real deal

An ObservableObject that owns the array of spaces and everything inside them. Creating a tab, closing one, pinning, moving into folders, switching spaces, renaming — every one of those is a method here, and SwiftUI redraws whatever changed.

It also handles persistence: state saves to state.json in Application Support (debounced, not on every keystroke), reloads at launch, and prunes ephemeral tabs older than 24 hours. The flow is one-directional and boring in the best way: view → store method → published change → view updates. When a feature misbehaves, set a breakpoint in the relevant store method and you'll usually have your answer.

The real deal

Shortly after a shell shows real activity, it asks an agent CLI (claude by default; configurable) to summarize what the terminal is doing and names the tab once. AgentSessionAdapter.swift

The real deal

Also defines the quit snapshot: written on every consented quit, it lets the next launch tell "was running when you quit" (restore it) from "crashed" (fall back to per-agent policies). The snapshot is consumed — deleted — after being read once, so a stale one can't lie twice.

AgentLaunchSanitizer.swift
macos/Enso/Services/AgentLaunchSanitizer.swift
196 lines

Agent persistence · scrubs a recorded launch command before replaying it on restore.

The real deal

Three tiers per agent: preserved options survive the replay (model, permission mode, MCP config); dropped ones are re-supplied by the restore itself (--resume, --session-id — dropping them is what makes restoring-a-restore idempotent); rejected ones (-p/--print) mean it was never an interactive session, so the whole restore is abandoned. Ported from cmux and trimmed to the agents Enso ships.

Journey — follow a click end to end

⌘N — a new tab is born

The fastest way to make a codebase feel familiar: trace one real action end to end. Here's everything that happens between pressing ⌘N and a blinking prompt.

  1. You press ⌘N. macOS routes it to the menu item declared in App/TerminalCommands.swift.
  2. The store makes a session. The command calls into Stores/TerminalSessionStore.swift, which appends a new TerminalSession to the current space's ephemeral zone and selects it.
  3. SwiftUI notices. The store is an ObservableObject; Views/SidebarView.swift re-renders and a new tab row appears.
  4. A surface is summoned. The terminal area asks Ghostty/GhosttySurfaceManager.swift for this session's surface. There isn't one yet, so it creates a GhosttySurfaceView.
  5. libghostty takes over. The new surface (via Ghostty/GhosttyRuntime.swift) opens a PTY, spawns your shell, and starts painting with Metal. From here, keystrokes flow down and screen updates flow up — Swift never sees the bytes.
  6. Later, it's saved. The store debounce-writes state.json, so the tab survives a relaunch (for 24h, unless you pin it).
Journey — follow a click end to end

🕵️ A tab realizes it's running claude

The signature feature: tabs that show what's actually running in them. Two independent detectors, one verdict.

  1. You run claude in a tab. Two independent detectors wake up.
  2. Signal one: the title. The shell's integration emits a title event; libghostty passes it up through Ghostty/GhosttySurfaceView.swift's callbacks.
  3. Signal two: the process table. Services/ForegroundProcessResolver.swift walks from the shell's pid to the pty's foreground process and finds a process literally named claude.
  4. The verdict. Models/TabProcess.swift combines both signals: this is a known agent → use the Claude brand mark.
  5. The sidebar updates. The tab row's badge swaps to the Claude logo; the palette and ⌃Tab switcher show the same thing via Views/RowProcessBadge.swift.
  6. Bonus: the name. Once the shell shows real activity, Services/TabAutoNamer.swift asks the claude CLI for a two-or-three-word summary and renames the tab — once, and never over a name you typed yourself.
Journey — follow a click end to end

🔁 Quit & resurrection

How a Claude conversation survives quitting the app. Four files conspire across two launches. Full design doc: docs/agent-session-persistence.md.

  1. While you work, the claude you're running is actually a wrapper shim (installed by Services/AgentShimInstaller.swift) that appends launch/session events to agent-sessions/<tab-uuid>.jsonl.
  2. You press ⌘Q. App/QuitGuard.swift counts live sessions and shows the confirmation alert. You say quit.
  3. A snapshot drops. A quit snapshot (defined in Services/AgentSessionAdapter.swift) records which tabs had agents running — this is how the next launch distinguishes a clean quit from a crash.
  4. Next launch. Services/AgentSessionStore.swift compacts each JSONL file to its latest session and — checking the snapshot and your Settings toggle — decides which tabs should resume.
  5. The command is scrubbed. Services/AgentLaunchSanitizer.swift filters the recorded argv: keep --model, drop the old --resume, abandon entirely if it was a one-shot -p run.
  6. Resurrection. The tab's new shell launches claude --resume <session> and your conversation continues where it left off.

The rest of the repo

Everything in the file breakdown lives in macos/. The other top-level folders:

cmux-alternative/
├─ macos/ ← the app. Enso.xcodeproj + everything this guide covers
│   └─ GhosttyKit.xcframework ← symlink to the engine, built from references/ghostty
├─ script/ ← build_and_run.sh (dev loop), release.sh (ship it), shim tests
├─ docs/ ← you are here · + agent-session-persistence.md deep dive
├─ references/ ← full source of ghostty & cmux, checked out for reading/building —
│     not part of the app target. Great for "how does Ghostty do X?"
├─ RELEASE_NOTES/ ← one markdown file per version; feeds the What's New sheet
├─ website/ ← the marketing site
├─ lab/ ← experiments & one-off tools (icon generator, etc.)
└─ internal-docs/ ← private notes, not shipped

One gotcha for building from source: GhosttyKit.xcframework isn't vendored. You build it once from references/ghostty with Zig and symlink it in — the exact commands are in the README.
